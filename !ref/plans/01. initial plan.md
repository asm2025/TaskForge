# TaskForge — Claude Code Plugin Showcase Plan

## Document Overview

- **Project**: TaskForge — Lightweight Task & Note Tracker
- **Purpose**: Internal demo to showcase Claude Code plugins (Orchestrator, sub-agents, skills)
- **Audience**: Engineering manager + team
- **Stack**: .NET 10 Web API + React 19 (Vite + TypeScript + Tailwind) + PostgreSQL 18, orchestrated by Docker Compose
- **Local domain**: `taskforge.local` resolved via `hosts` file → `127.0.0.1`
  - Backend (.NET API): `https://taskforge.local:44380`
  - Frontend (Vite dev server / static host): `https://taskforge.local:44385`
  - Postgres (Docker): `localhost:5532` (host port mapped to container `5432`)
- **Postgres data directory**: external host volume bind-mounted at `D:\Work\db\PostgreSQL-TaskForge`
- **Status**: Demo / sandbox — NOT production code
- **Today**: 2026-05-19

---

## Why This Project

The project must be:

- **Small enough** to finish a meaningful slice in a single demo session (1–2 hours of agent runtime).
- **Realistic enough** to exercise backend, frontend, database, tests, and docs — the same surface area as a real product, at ~1% the scope.
- **Disposable** — a separate repo, so real work is untouched.
- **Plugin-friendly** — each plugin must have at least one task it genuinely owns, otherwise the demo is theatre.

**Non-goal**: Production hardening, real auth providers, SAML, multi-DB. Out of scope.

## Scope of Work

### In Scope

1. **Backend** — ASP.NET Core 10 Web API (`TaskForge.Api`)
   - `Tasks` resource: CRUD (`GET/POST/PUT/DELETE /api/tasks`)
   - `Notes` resource: CRUD attached to a task (`/api/tasks/{taskId}/notes`, `/api/notes/{id}` for PUT/DELETE)
   - EF Core 10 + Npgsql, single `AppDbContext`
   - Migrations auto-applied on startup when `DatabaseMigrationsConfiguration:ApplyDatabaseMigrations = true`
   - Seed data merged on startup from `seed.json` + `seed.{Environment}.json` (see *Seeding* section)
   - FluentValidation for DTOs
   - Serilog → console (structured JSON) + rolling file
   - xUnit + `WebApplicationFactory` integration tests for `Tasks` and `Notes` controllers
2. **Frontend** — React 19 + Vite 6 + TypeScript + Tailwind 4
   - Pages: `/` (task list), `/tasks/:id` (detail + notes)
   - TanStack Query v5 for server state
   - Notes rendered as Markdown (`react-markdown` + `remark-gfm`) with edit-in-place
   - Component tests with Vitest + Testing Library
   - One Playwright smoke test: create task → add note (markdown) → reload → still there, rendered as HTML
   - **No Zustand** — there is no real shared UI state for this scope; removing it removes dead code reviewers would flag.
3. **Database** — PostgreSQL 18 in Docker, host-bound external volume at `D:\Work\db\PostgreSQL-TaskForge`, healthcheck
4. **Infra** — `docker-compose.yml` runs `db`, `api`, `web` with healthchecks; one-command boot: `docker compose up`
5. **Tooling scripts** (Windows-first, with `.sh` parity stubs):
   - `cert.bat` — generate + optionally trust a self-signed cert for `taskforge.local`
   - `js.bat` — multi-project pnpm/bun/yarn/npm runner (install/update/build/clean/list/audit/outdated)
   - `migrate.bat` — `dotnet-ef` wrapper (`add`/`remove`/`list`/`update`) targeting `AppDbContext`
   - **No `seed.bat`** — seeding is a responsibility of the API process itself. See *Seeding* section.
6. **Docs** — `README.md` (root, comprehensive), `ARCHITECTURE.md`, `CONTRIBUTING.md`, `DEMO_SCRIPT.md`, `CLAUDE.md`

### Explicitly Out of Scope

- Authentication / authorization (note this loudly in `README.md` and `SECURITY.md`)
- CI/CD beyond a single GitHub Actions workflow that runs **native** `dotnet test` + `pnpm test` (no Docker in CI)
- Real deployment, TLS termination at a reverse proxy, secrets management

## Plugin Roles (Concrete Triggers + Outputs)

All twelve plugins are installed. The demo only **uses** six core plugins, plus the install of one as a live example. The other plugins are mentioned by name only.

### Core six — every one has a concrete trigger, output sink, and pass/fail signal

| Plugin | Trigger | Output sink | Pass/fail signal |
|---|---|---|---|
| `superpowers` | Implicit (Orchestrator skill loaded at session start) | Transcript + this plan file | Orchestrator declares slice done when exit criteria green |
| `skill-creator` | Manual: `/skill-creator new add-crud-resource` after `Tasks` slice merges | `.claude/skills/add-crud-resource/SKILL.md` | Skill file exists; reused on `Notes` slice |
| `claude-md-management` | `/claude-md-management revise` at end of each slice | `CLAUDE.md` diff | New conventions present in `CLAUDE.md` |
| `code-review` | `/code-review` on the working diff before PR open | PR review comments (via `github`) | Only `error`/`high` findings block; `nit`/`info` are advisory |
| `code-simplifier` | `/code-simplifier api/TaskForge.Api/Controllers/TasksController.cs` after first green build | Diff applied in-place | Reviewer accepts the simplification |
| `github` | `/commit-push-pr` after exit-criteria pass | Live PR on GitHub | PR opened, CI green, review thread closed |

### Severity policy for `code-review`

- `error` / `high` → **blocks** loop exit, must be addressed.
- `medium` → must be addressed OR explicitly waived with a one-line justification in the PR description.
- `low` / `nit` / `info` → advisory; logged in PR but does not block.

This stops `code-review` from being noise and gives the Orchestrator a clean exit signal.

### Fallback rule

If any plugin is unavailable at runtime, the Orchestrator logs a `WARN: plugin <name> not available, skipping <step>` and proceeds. Only `code-review` failure is fatal (others are advisory).

### Other six plugins — mentioned, not driven

`frontend-design`, `security-guidance`, `ralph-loop`, `playwright`, `terraform`, `typescript-lsp`.

**Live install example**: install `frontend-design` on camera at the start of the demo, then immediately use it to generate the `/tasks/:id` page layout. Everything else is name-checked in `DEMO_SCRIPT.md` with one sentence each on what it would own if used.

**`terraform`**: skipped on purpose — no cloud target.

## Workflow — Orchestrator Loop

Each feature slice (e.g. *"add Notes resource"*) runs through this loop. The Orchestrator (`superpowers`) drives it:

1. **Plan** — Orchestrator reads `01. initial plan.md` + `CLAUDE.md`, breaks the slice into ≤5 tasks.
2. **Implement** — Implementer sub-agent picks one task. If a matching skill exists in `.claude/skills/`, it uses it. Otherwise on the *second* occurrence of a CRUD pattern (i.e. after `Tasks` is done), the Orchestrator manually invokes `skill-creator` to extract one.
3. **Self-check** — Implementer runs `dotnet test` / `pnpm test` locally before handing off.
4. **Review** — `code-review` sub-agent reviews the diff. Findings go back to Implementer using the severity policy above. Repeat until clean.
5. **Simplify (optional)** — On files flagged as complex, `code-simplifier` proposes a reduction. Orchestrator decides whether to accept.
6. **Docs sync** — `claude-md-management` updates `CLAUDE.md` if conventions, commands, or architecture changed.
7. **Exit check** — Orchestrator verifies the slice's exit criteria (below). If green, `github` opens/updates the PR.

| `due_at`      | `timestamptz` NULL |                                               |
| `created_at`  | `timestamptz` NOT NULL | UTC, server-set                            |

### `notes`

| Column        | Type              | Notes                                                  |
|---------------|-------------------|--------------------------------------------------------|
| `id`          | `uuid` PK         | Server-generated                                       |
| `task_id`     | `uuid` FK → tasks(id) ON DELETE CASCADE | Required                          |
| `body`        | `text` NOT NULL   | **Markdown source**, 1–10000 chars. Rendered to HTML client-side. |
| `created_at`  | `timestamptz` NOT NULL | UTC                                               |
| `updated_at`  | `timestamptz` NOT NULL | UTC, server-set on every update                   |

Indexes: `idx_notes_task_id` on `notes(task_id)`, `idx_tasks_status` on `tasks(status)`.

### CRUD endpoints

```
GET    /api/tasks                       → 200 [TaskDto]
POST   /api/tasks                       → 201 TaskDto
GET    /api/tasks/{id}                  → 200 TaskDto | 404
PUT    /api/tasks/{id}                  → 200 TaskDto | 404
```

## Seeding

Seeding lives inside the API process. There is **no** external `seed.bat`. The behavior mirrors `ApplyDbMigrationsWithDataSeedAsync` from the reference `Program.cs`:

### Configuration chain (in `CreateHostBuilder`)

```csharp
configurationBuilder
    .AddJsonFile("appsettings.json", optional: false, reloadOnChange: true)
    .AddJsonFile($"appsettings.{env}.json", optional: true, reloadOnChange: true)
    .AddJsonFile("seed.json", optional: false, reloadOnChange: true)
    .AddJsonFile($"seed.{env}.json", optional: true, reloadOnChange: true)
    .AddEnvironmentVariables()
    .AddCommandLine(args);
```

### CLI args (mirrors the reference)

```csharp
private const string SeedArgs = "/seed";
private const string MigrateOnlyArgs = "/migrateonly";
```

- `/seed` — force a seed pass on this run regardless of `SeedConfiguration:Enabled`.
- `/migrateonly` — apply migrations + (conditional) seed, then exit before `app.RunAsync()`.

### Startup flow in `Main`

```csharp
WebApplication app = builder.Build();

bool migrationComplete = await ApplyDbMigrationsWithDataSeedAsync(args, configuration, app, logger);
if (!migrationComplete)
{
    Environment.ExitCode = -1;
    await app.StopAsync();
    return;
}

if (args.Any(a => string.Equals(a, MigrateOnlyArgs, StringComparison.OrdinalIgnoreCase)))
    return;

ConfigureApp(app);
await app.RunAsync();
```

### `ApplyDbMigrationsWithDataSeedAsync` (TaskForge version)

Single-context simplification of the reference helper:

```csharp
private static async Task<bool> ApplyDbMigrationsWithDataSeedAsync(
    string[] args,
    IConfiguration configuration,
    IHost host,
    ILogger logger)
{
    logger.LogInformation("Checking database migration.");

    bool forceSeedFromArgs = args.Any(a =>
        string.Equals(a, SeedArgs, StringComparison.OrdinalIgnoreCase));

    SeedConfiguration seedCfg = configuration
        .GetSection(nameof(SeedConfiguration))
        .Get<SeedConfiguration>() ?? new SeedConfiguration();

    DatabaseMigrationsConfiguration dbMigCfg = configuration
        .GetSection(nameof(DatabaseMigrationsConfiguration))
        .Get<DatabaseMigrationsConfiguration>() ?? new DatabaseMigrationsConfiguration();

    using IServiceScope scope = host.Services.CreateScope();
    var sp = scope.ServiceProvider;
    var db = sp.GetRequiredService<AppDbContext>();

    try
    {
        if (dbMigCfg.ApplyDatabaseMigrations)
        {
            logger.LogInformation("Applying migrations...");
            await db.Database.MigrateAsync();
        }

        bool shouldSeed = forceSeedFromArgs || seedCfg.Enabled;
        if (shouldSeed)
        {
            logger.LogInformation("Seeding data (strategy: {Strategy})...", seedCfg.MergeStrategy);
            await DataSeeder.SeedAsync(db, configuration, seedCfg, logger);
        }

        logger.LogInformation("Database migration completed successfully.");
        return true;
    }
    catch (Exception ex)
    {
        logger.LogError(ex, "Database migration did not complete successfully.");
        return false;
    }
}
```

`DataSeeder.SeedAsync` reads `Tasks[]` (and any future seed sections) from the merged configuration, and applies them per `seedCfg.MergeStrategy` (`upsertByTitle` by default). Idempotent.

### When does seed actually run?

| Env       | `SeedConfiguration:Enabled` default | `/seed` arg | Behavior                                |
|-----------|-------------------------------------|-------------|-----------------------------------------|
| `Debug`   | `true`                              | —           | Auto-seed on every startup              |
| `Stage`   | `true`                              | —           | Auto-seed on every startup              |
| `Release` | `false`                             | absent      | No seed (only migrations)               |
| `Release` | `false`                             | `/seed`     | One-shot seed on this run               |
| any       | any                                 | `/migrateonly` | Migrate + (conditional) seed, then exit |

### One-shot manual seed (no `seed.bat` needed)

```cmd
dotnet run --project api/TaskForge.Api -- /seed
```

Or against a built image:

```cmd
docker compose run --rm api dotnet TaskForge.Api.dll /seed
```

### `seed.json` example

```json
{
  "SeedConfiguration": {
    "Enabled": true,
    "MergeStrategy": "upsertByTitle"
  },
  "Tasks": [
    { "title": "Write demo plan",         "status": "done",  "priority": 2 },
    { "title": "Wire docker-compose",     "status": "doing", "priority": 2 },
    { "title": "Build Tasks CRUD",        "status": "doing", "priority": 1 },
    { "title": "Build Notes CRUD",        "status": "todo",  "priority": 1 },
    { "title": "Record demo walkthrough", "status": "todo",  "priority": 0 }
  ]
}
```

`seed.Debug.json` / `seed.Stage.json` may override per environment.

`MergeStrategy: upsertByTitle` means: existing rows with the same `title` are updated; missing rows are inserted; nothing is deleted.

## Phase Plan (Execution Order)

Phases 1 and 2 run **in parallel**. The Orchestrator dispatches them to two Implementer sub-agents.

### Phase 0 — Repo bootstrap (single agent, ~5 min)

- `git init`, license, `.gitignore`, root scaffolding folders.
- Write `global.json` pinning `sdk.version = "10.0.100"` (or whatever's current at demo time — verify via `dotnet --list-sdks`).
- Add `taskforge.local` to `C:\Windows\System32\drivers\etc\hosts` mapping to `127.0.0.1` (instruct user to do this; cannot be automated without admin).

### Phase 1 — Tooling scripts (parallel sub-agent A)

Produce, in parallel, in this phase:

1. **`cert.bat`** — clone the reference cert.bat behavior, adapted for `taskforge.local`:
   - Subcommands: `gen` / `generate`, `trust`, `setup` (default), `help`.
   - Generates `taskforge.local.crt` + `.key` + `.pfx` (password-free) into `docker\certs\` using OpenSSL.
   - Subject: `/C=US/ST=State/L=City/O=TaskForge/CN=taskforge.local`.
   - SAN: `DNS:taskforge.local,DNS:localhost,IP:127.0.0.1,IP:::1`.
   - 365-day validity.
   - `trust` step uses `certutil -addstore -f "Root" ...`; checks admin.
   - `setup` runs `gen` then prompts to `trust`.
   - Companion `cert.sh` for parity (mkcert or openssl).
2. **`js.bat`** — multi-project package-manager runner:
   - Commands: `install` / `update` / `build` / `clean` / `list` / `audit` / `outdated`.
   - Flags: `-c` (CI / frozen lockfile), `-m <pm>` (force pnpm/bun/yarn/npm; default pnpm).
   - Iterates over project paths: `web`, `e2e`.
   - Falls back to next available PM with a one-time warning if the preferred one is missing.
3. **`migrate.bat`** — `dotnet-ef` wrapper:
   - Operations: `add <Name> AppDbContext <Folder>`, `remove AppDbContext`, `list AppDbContext`, `update AppDbContext`, `help`.
   - Project: `api/TaskForge.Api`, startup-project: same.

### Phase 2 — Infra + DB (parallel sub-agent B)

## Conventions (seed for `CLAUDE.md`)

These are starting conventions. `claude-md-management` keeps them current.

- **IDs**: `Guid` (not `int`). Generated server-side via `Guid.NewGuid()`.
- **Timestamps**: `DateTimeOffset` (UTC). `created_at` / `updated_at` on every entity. `updated_at` set in `SaveChangesAsync` interceptor.
- **Errors**: API returns RFC 7807 `ProblemDetails`.
- **Naming**: `PascalCase` for .NET, `camelCase` for TS, `snake_case` for SQL columns.
- **Migrations**: auto-applied in `Debug`/`Stage`/`Release` when `DatabaseMigrationsConfiguration:ApplyDatabaseMigrations = true`. Never edit a committed migration.
- **Commit style**: Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, `test:`).
- **Branching**: one branch per slice, `demo/<slice-name>`.
- **Markdown**: `Note.body` stores raw markdown. Sanitize on render with `rehype-sanitize`.

## Security Posture (be explicit)

This is a **demo on localhost only**. The following are *intentionally* absent and must not be added without re-scoping:

- No authentication, no authorization. All endpoints are open.
- No rate limiting, no CSRF, no CORS lockdown (CORS is `AllowAll` for the demo).
- Database credentials are in plain `docker-compose.yml`. Acceptable because the DB is bound to `localhost:5532` and the bind mount is local-only.
- Self-signed TLS cert. Production would use a real CA.

`SECURITY.md` lists each of the above with a one-line justification.

## CI

Single GitHub Actions workflow `.github/workflows/ci.yml`:

- Runs on push + PR.
- Two jobs in parallel:
  - **api**: `dotnet restore` → `dotnet build` → `dotnet test` (no Docker — uses Testcontainers, which spins up PG on the GitHub runner's Docker daemon).
  - **web**: `pnpm install --frozen-lockfile` → `pnpm test` → `pnpm build`.
- No deployment step.
- Native (not via `docker compose`) for speed and to avoid duplicating runtime config.

## Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Demo runs over time during a live session. | High | Medium | Pre-recorded fallback for every act; hard time-box per act. |
| `taskforge.local` not in `hosts` on the demo machine. | Medium | High | Pre-flight check; document the one-line fix in `README.md`. |
| `D:\Work\db\PostgreSQL-TaskForge` permissions block the bind mount. | Low | High | Pre-flight: create the folder; if PG can't write, fall back to a named docker volume. |
| Plugins conflict or shadow each other's tools. | Medium | Medium | Enable plugins one at a time on first run; pre-record the working combo. |
| `code-review` produces noise, not signal. | Medium | Low | Severity policy above; tune its prompt in `CLAUDE.md`; show the tuning as part of the demo. |
| Self-signed cert not trusted → browser blocks frontend. | Medium | Medium | `cert.bat trust` in pre-flight; document the per-browser bypass in `README.md`. |
| Confusion between this demo repo and real work. | Low | High | Separate GitHub repo; no shared `CLAUDE.md`; explicit "demo only" banner in `README.md`. |
