# Demo Project Plan — Claude Code Plugin Showcase

## Document Overview

**Project**: TaskForge — Lightweight Task & Note Tracker
**Purpose**: Internal demo to showcase Claude Code plugins (Orchestrator, sub-agents, skills)
**Audience**: Engineering manager + team
**Stack**: .NET 10 Web API + React 19 (Vite + TypeScript) + PostgreSQL 18, all via Docker Compose
**Status**: Demo / sandbox — NOT production code

---

## Why This Project

The project must be:

- **Small enough** to finish a meaningful slice in a single demo session (1–2 hours of agent runtime).
- **Realistic enough** to exercise backend, frontend, database, tests, and docs — the same surface area as `Vigilix Platform` and `Plan 18 Residual Hardening`, but at ~1% the scope.
- **Disposable** — a separate repo, so my real Vigilix work is untouched.
- **Plugin-friendly** — each plugin must have at least one task it genuinely owns, otherwise the demo is theatre.

**Non-goal**: Production hardening, real auth providers, SAML, multi-DB. Those belong to the real Vigilix plan.

---

## Scope of Work

### In Scope

1. **Backend** — ASP.NET Core 10 Web API
   - `Tasks` resource: CRUD (`GET/POST/PUT/DELETE /api/tasks`)
   - `Notes` resource: CRUD attached to a task (`/api/tasks/{id}/notes`)
   - EF Core 10 + Npgsql, single `AppDbContext`, auto-migrate on startup in `Development`
   - FluentValidation for DTOs
   - Serilog → console (structured JSON)
   - xUnit + `WebApplicationFactory` integration tests for at least the `Tasks` controller
2. **Frontend** — React 19 + Vite + TypeScript + Tailwind
   - Pages: `/` (task list), `/tasks/:id` (detail + notes)
   - TanStack Query for server state, Zustand for trivial UI state
   - Component tests with Vitest + Testing Library
   - One Playwright smoke test: create task → add note → reload → still there
3. **Database** — PostgreSQL 18 in Docker, persisted volume, seed script with 5 tasks
4. **Infra** — `docker-compose.yml` runs `db`, `api`, `web` with healthchecks; one-command boot: `docker compose up`
5. **Docs** — `README.md`, `ARCHITECTURE.md`, `CONTRIBUTING.md`, `DEMO_SCRIPT.md`

### Explicitly Out of Scope

- Authentication / authorization (note this loudly in README — see *Security Posture* below)
- CI/CD beyond a single GitHub Actions workflow that runs build + test
- Real deployment, TLS, secrets management

## Workflow — Orchestrator Loop

Each feature slice (e.g. *"add Notes resource"*) runs through this loop. The Orchestrator (`superpowers`) drives it:

1. **Plan** — Orchestrator reads `01. initial plan.md` + `CLAUDE.md`, breaks the slice into ≤5 tasks.
2. **Implement** — Implementer sub-agent picks one task. If a matching skill exists in `.claude/skills/`, it uses it. Otherwise, on the second occurrence of a pattern, it asks `skill-creator` to extract one.
3. **Self-check** — Implementer runs `dotnet test` / `pnpm test` locally before handing off.
4. **Review** — `code-review` sub-agent reviews the diff. Findings go back to Implementer. Repeat until clean.
5. **Simplify (optional)** — On files flagged as complex, `code-simplifier` proposes a reduction. Orchestrator decides whether to accept.
6. **Docs sync** — `claude-md-management` updates `CLAUDE.md` if conventions, commands, or architecture changed.
7. **Exit check** — Orchestrator verifies the slice's exit criteria (below). If green, `github` opens/updates the PR.

---

## Exit Criteria

A feature slice is **done** only when **all** of these hold. The Orchestrator must verify each before closing the loop.

### Per-Slice Exit Criteria

- [ ] `docker compose up` boots cleanly from a fresh clone, no manual steps.
- [ ] `dotnet test` is green; ≥1 integration test covers the new endpoint.
- [ ] `pnpm test` is green; ≥1 component test covers the new UI.
- [ ] `code-review` has no open findings on the diff.
- [ ] `CLAUDE.md` reflects any new conventions, commands, or files introduced.
- [ ] PR description on GitHub lists: what changed, how to verify, what was *not* done.
- [ ] No secrets, no `TODO` without an issue link, no commented-out code.

### Whole-Demo Exit Criteria

- [ ] Two feature slices completed via the loop (`Tasks`, then `Notes`).
- [ ] At least one skill authored by `skill-creator` and reused.
- [ ] At least one `code-review` finding raised and resolved on-camera.
- [ ] At least one `code-simplifier` before/after diff captured.
- [ ] `README.md` has a *"Plugins used and why"* section linking to the transcript.
- [ ] `DEMO_SCRIPT.md` reproduces the demo in ≤30 minutes from `git clone`.

## Conventions (seed for `CLAUDE.md`)

These are starting conventions. `claude-md-management` is responsible for keeping them current.

- **IDs**: `Guid` (not `int`). Generated server-side.
- **Timestamps**: `DateTimeOffset` (UTC), `created_at` / `updated_at` on every entity.
- **Errors**: API returns RFC 7807 `ProblemDetails`.
- **Naming**: `PascalCase` for .NET, `camelCase` for TS, `snake_case` for SQL columns.
- **Migrations**: auto-applied in `Development`; never edit a committed migration.
- **Commit style**: Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, `test:`).
- **Branching**: one branch per slice, `demo/<slice-name>`.

## Security Posture (be explicit)

This is a **demo on localhost only**. The following are *intentionally* absent and must not be added without re-scoping:

- No authentication, no authorization. All endpoints are open.
- No rate limiting, no CSRF, no CORS lockdown (CORS is `AllowAll` for the demo).
- Database credentials are in plain `docker-compose.yml`. Acceptable because the DB is not reachable outside the compose network.

`security-guidance` (if enabled) owns `SECURITY.md` and must list each of the above with a one-line justification.

## Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Demo runs over time during a live session. | High | Medium | Pre-record the loop; live-walk through the artifacts. |
| Plugins conflict or shadow each other's tools. | Medium | Medium | Enable plugins one at a time on first run; record which combo works. |
| `code-review` produces noise, not signal. | Medium | Low | Tune its prompt in `CLAUDE.md`; show the tuning as part of the demo. |
| `terraform` / `security-guidance` tempt scope creep. | Medium | Medium | Hard line: `terraform` is out. `security-guidance` only writes `SECURITY.md`. |
| Confusion between this demo repo and real Vigilix work. | Low | High | Separate GitHub org/account or clearly-prefixed repo name; no shared `CLAUDE.md`. |
